## Bins and expectations

### L1-00 Modular PMA software module frame and shell conformance
Applies: Every modular PMA software module
- **L2-00.01** Accepted shell entry for the software module (importance 2; entities: document, date)
  Expect: The module's declared contents and projected date match the FDA-accepted shell, or a shell change was agreed.
- **L2-00.02** Module required front matter (importance 2; entities: document, date, person_or_org)
  Expect: Cover letter, TOC, executive summary of testing and results, brief device description and principles of operation, module DoC section and bibliography are present.
- **L2-00.03** Post-acceptance change and module reopening (importance 3; entities: software_version, document, date)
  Expect: If the device changed after FDA accepted a module, the affected modules carry an amendment with revised executive summary, change description, list of repeated testing and supporting data.

### L1-01 Documentation Level evaluation
Applies: Every device with device software functions
- **L2-01.01** Documentation Level statement and rationale (importance 2; entities: document, hazardous_situation)
  Expect: A statement of Basic or Enhanced level with device-specific rationale referencing the risk file and software description; Class III defaults to Enhanced unless justified.
- **L2-01.02** IEC 62304 software safety classification and rationale (importance 2; entities: software_version, design_component, document)
  Expect: Each software system (and, where decomposed, each software item) carries a software safety class A, B or C assigned from the worst-case severity of the hazardous situation it can contribute to, with the 100 percent failure-probability assumption, any reduction via hardware risk controls, and segregation claims used for item-level classification. The class is distinct from the FDA Documentation Level and decides which IEC 62304 clauses a DoC can claim.

### L1-03 Software version and configuration identification
Applies: Every device with device software functions; anchor bin for all version joins
- **L2-03.01** Proposed release version and version naming rules (importance 3; entities: software_version)
  Expect: The released software version is documented with the naming rule that distinguishes major/minor/build and is identifiable to the user.
- **L2-03.02** Release build identity and build environment (importance 3; entities: software_version, document)
  Expect: The build of the release candidate is uniquely identified and the procedure/environment used to create it is documented; integrity mechanism exists.
- **L2-03.03** Configuration item list (software system configuration) (importance 3; entities: software_version, soup_component, design_component)
  Expect: The set of configuration items and their versions comprising the system configuration is documented, including SOUP, data/model/reference files and platform components.
- **L2-03.04** Baseline dates: code freeze and release (importance 2; entities: date, software_version)
  Expect: Code freeze/baseline date and release date are recorded; release only after verification complete.

### L1-04 Risk management file (safety)
Applies: Every device with device software functions
- **L2-04.01** Risk management plan (importance 3; entities: document, person_or_org, date)
  Expect: Plan states scope/lifecycle phases, responsibilities, review requirements, individual risk acceptability criteria (incl. when probability cannot be estimated), overall residual risk method/criteria, verification activities and post-production activities.
- **L2-04.02** Intended use, foreseeable misuse and safety characteristics (importance 2; entities: document)
  Expect: Intended use, reasonably foreseeable misuse and characteristics related to safety are documented.
- **L2-04.03** Hazards, sequences of events and hazardous situations (software incl.) (importance 3; entities: hazard, hazardous_situation, design_component)
  Expect: Known/foreseeable hazards with causes, software items contributing, sequences of events and resulting hazardous situations are identified, including SOUP anomaly-related causes.
- **L2-04.04** Initial risk estimation and evaluation (importance 2; entities: hazardous_situation, date)
  Expect: Each hazardous situation has an estimated risk and an acceptability decision using the plan's criteria.
- **L2-04.05** Risk control measures and their verification (implementation and effectiveness) (importance 3; entities: risk_control, requirement, test_case, test_run)
  Expect: Each control is classified (design/protective/information), traced to SRS/SDS and to tests or other evidence verifying implementation and, separately, effectiveness; new risks from controls assessed.
- **L2-04.06** Residual risk evaluation and benefit-risk (importance 2; entities: hazardous_situation, risk_control)
  Expect: Residual risk per hazardous situation is evaluated against plan criteria; unacceptable residual risks have benefit-risk analysis.
- **L2-04.07** Overall residual risk and disclosure (importance 2; entities: document, risk_control)
  Expect: Overall residual risk evaluated with the plan's method; significant residual risks disclosed in accompanying documentation.
- **L2-04.08** Risk management report / review (importance 3; entities: document, person_or_org, date)
  Expect: Report shows plan implemented, overall residual risk acceptable, production/post-production methods in place, reviewed by assigned persons.
- **L2-04.09** Production and post-production information system (importance 1; entities: document)
  Expect: System to collect and review production/post-production information, including feedback into risk file.
- **L2-04.10** Safety traceability matrix document (hazard - requirement - design - test) (importance 2; entities: document, hazard, requirement, test_case)
  Expect: Where the HAZ -> SRS/SDS -> UT/INT/SYS trace is presented as a separate document (FDA-SW VI.C(2)), the document is identified with version, export date and the software version it covers, and its rows reconcile with the per-artifact links captured in L2-04.05, L2-05.02, L2-07.01 and L2-09.02.

### L1-05 Software requirements specification (SRS)
Applies: Every device with device software functions
- **L2-05.01** Requirement identification and traceability method (importance 2; entities: document, requirement)
  Expect: SRS describes the requirement ID scheme and the tracking method supporting traceability to risk, design, architecture and tests.
- **L2-05.02** Individual software requirements (importance 3; entities: requirement)
  Expect: Each requirement is uniquely identified, testable and categorized; safety requirements derived from risk controls are included.
- **L2-05.03** Security requirements in SRS (importance 2; entities: requirement, security_control)
  Expect: Security requirements and acceptance criteria exist for each applicable control category and are reviewed.
- **L2-05.04** Requirements approval and change control (importance 2; entities: document, date, person_or_org)
  Expect: SRS approval with date/signature; changes after baseline are controlled; differences vs prior version highlighted (modified device).

### L1-09 Software testing as part of verification and validation
Applies: Every device; Enhanced requires unit and integration protocols/reports
- **L2-09.01** Verification planning and test strategy by level (importance 2; entities: document)
  Expect: Plan defines unit, integration and system test levels, entry/exit criteria, environments and acceptance criteria.
- **L2-09.02** Test cases and protocols with expected results and approval (importance 3; entities: test_case, requirement, date)
  Expect: Protocols list test cases with inputs, steps and expected results derived from requirements/design and objective pass/fail criteria; approved before execution.
- **L2-09.03** Unit and integration level protocols, results and reports (Enhanced) (importance 3; entities: test_case, test_run, test_report, interface)
  Expect: All unit and integration protocols and reports with expected/actual results and pass/fail; reports show acceptable execution and deferral of unresolved anomalies for the candidate release.
- **L2-09.04** Test environments and configurations (importance 2; entities: design_component, soup_component, software_version)
  Expect: Each environment is specified (hardware, OS, OTS versions, tools, simulators, data sets) and its readiness recorded.
- **L2-09.05** System-level test execution records (importance 3; entities: test_run, software_version, date, person_or_org)
  Expect: Each system test run records procedure reference, result and anomalies, software version, hardware/software configuration, tools, date and person.
- **L2-09.06** Failed tests, intentional changes, regression analysis and regression testing (importance 3; entities: test_run, anomaly, software_version, document)
  Expect: Changes made in response to failures are documented with evidence they were implemented correctly; a documented regression analysis determines which tests re-run, with pass/fail results.
- **L2-09.07** Test reports (system, unit, integration) (importance 3; entities: test_report, software_version, date)
  Expect: Reports state what was executed, results, deviations, residual anomalies and conclusion for the candidate release version.
- **L2-09.08** Testing summary and declared test window (importance 2; entities: test_report, software_version, date)
  Expect: Summary of unit/integration/system activities with software version tested and overall pass/fail per protocol.
- **L2-09.09** Software validation in actual or simulated use environment (importance 3; entities: test_run, test_report, requirement)
  Expect: Evidence that specifications conform to user needs and intended uses in actual/simulated use, integrated into final device where appropriate.
