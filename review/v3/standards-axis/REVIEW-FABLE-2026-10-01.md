## B. Chain audit

All 25 chains were read; every backticked `L2-xx.yy.parameter` reference resolves against `BIN-HIERARCHY.json` (checked by script; 0 unresolved). Findings:

**Wrong or over-stated**

- **CC-06**: "These sets are equal: unresolved list, security-assessed set, and deferred set in the reports." Only two of the three relations hold. Every unresolved anomaly must be security-assessed (FDA-CY V.A.5 applies to the whole list), so unresolved = security-assessed. But the test reports' `deferred_anomaly_ids` are anomalies deferred *from testing*; anomalies found in reviews, static analysis or field use (FDA-SW VI.J: "review, test, analysis, compilation, or use") are unresolved without being deferred by any test report. Correct relation: deferred ⊆ unresolved; a deferred anomaly missing from the unresolved list is the S3 break.
- **CC-04**: "`fixed_in_build <= A.release_build_id`" assumes an order on build ids, but the normalization rules say build ids are compared exactly. Define the order through `L2-10.01` (the build must appear at or before the release entry).
- **CC-05**: `L2-14.01.configuration_covered` must equal `A.proposed_version` is too strong. A threat model is scoped to an architecture/configuration (IEC 81001-5-1 7.2 "current development scope"), not to a release string; its currency is already policed by CC-12 r. Treat the threat model as a descriptive document (S2) in CC-05. Same for `L2-28.04.software_version_covered_by_doc` when the DoC is to a process standard.
- **CC-12 f**: the source rule "FDA-STD IV.A final finished device" governs testing behind a *DoC*; it is not a rule about penetration tests. The right sources are FDA-CY V.C (test reports submitted) plus FDA-CY VII.D (changes that may impact cybersecurity) and FDA-SW VI.I (tested vs released). The condition itself is right.
- **CC-12 p**: IEC 62304 7.1.3 requires that the evaluated anomaly list be "relevant to the version of the SOUP item used"; it says nothing about the review date following the configuration entry date. A review performed before the version was frozen, on the same version, satisfies 7.1.3. Replace the date-order test with the version-equality test already in CC-03 and keep the review's *age* as the judgment item. Downgrade p to S1 or delete it.
- **CC-12 c**: S3 for `L2-16.01.sbom_generation_date` earlier than code freeze is harsh; an SBOM generated from an unchanged component manifest can be valid, and CC-11 catches content mismatch. S2.
- **CC-12 n**: there is no cited rule that the security plan must be approved before the first security risk evaluation; it is by analogy to FDA-SW VI.C(1). Mark the source as "by analogy" so a reviewer does not cite SW96 for it.
- **CC-12 o**: S3 unconditionally; FDA-MODPMA VI.C(4) makes the amendment conditional on a "major change" judgement. Keep as S3 candidate with a reviewer qualifier.
- **CC-23**: labelled Judgment only. With IEC 62443-4-1 Table 3 (see A.15) the independence level per test type is a mechanical comparison; adequacy of "means of objectivity" (IEC 81001-5-1 5.7.5) stays judgment. Type: Mixed.

## C. Ruling on the coordinator's six points

### Point 1. Importance inflation — **modify**

Agree that 80 of 172 at importance 3 is too many; the eight security-control-category L2s, the five architecture views and the labeling items are the clearest inflation (FDA-CY VI.A introduces the labeling list as "examples of information that may be included"). I disagree with the target of 35 and with some of the names on it.

Reasons to hold more than 35:

- The coordinator's list drops the safety risk file entirely while keeping "risk control verification", which is L2-04.05. The plan (L2-04.01: FDA-SW VI.C(1) says the Agency "intends to primarily focus on" acceptability criteria and the overall-residual-risk method), the hazard table (L2-04.03, root of CC-02) and the report (L2-04.08, FDA-SW VI.C(3)) are decision-critical for a module whose scope includes risk management.
- Unit and integration protocols/reports (L2-09.03) are the one deliverable that distinguishes Enhanced from Basic in FDA-SW Table 1. Lowering it defeats the profile's stated level.
- The security risk management report (L2-13.02) is the first row of FDA-CY Appendix 4 Table 1 and carries the residual security risk conclusion.
- Known-vulnerability and SBOM-derived evidence (L2-17.01, 17.02, 16.02) are where "SBOM date versus proposed build" actually bites.
- For a cyber device, the CVD process and patch timelines (L2-25.04, 25.05) are statutory under 524B(b)(1)–(2), not recommendations.
- Modular-PMA-specific: post-acceptance change (L2-00.03) silently invalidates every verified-build join.

Reasons to lower items the coordinator did not name: L2-02.03 (duplicate of the L1-03 anchor), L2-03.04 (its dates matter through CC-12, not by presence), L2-05.03 and L2-07.01 (covered by L1-21 and CC-01), L2-12.06 (covered by CC-11/CC-18), L2-15.01 (method; its effect is tested by the new CC-26), L2-18.01 and L2-19.01 (derived from L1-11 and CC-04), L2-28.04/28.05, L2-29.01 (labeling is filed in the final module), L2-04.07 (duplicated by L2-04.08).

### Point 2. `required_enhanced` over-marking and the DHF/submission split — **agree, with the evidence and the list**

The split is right and it has a textual basis the hierarchy should cite:

- FDA-SW Table 1 Enhanced column: SDS; "complete configuration management and maintenance plan document(s)"; system protocols with expected results, observed results, pass/fail and report; unit and integration protocols and reports; version history; anomaly list. Nothing about per-run tester identity, tool versions or build identifiers.
- FDA-SW VI.F Basic: "Sponsors should document this information ... via the DHF ... FDA may request additional information, if needed." FDA-OTS III.D Basic uses the same formula. These are the model for a third state.
- FDA-STD IV.A: "accompanying test data is not required to be submitted with a DOC ... FDA may request, at any time, the data ... Such records are part of the design history file."
- IEC 62304 5.7.5 b) (as amended) and 5.6.7 b): "retain sufficient records to permit the test to be repeated" — a retention duty, not a submission duty.
- Against that, FDA-CY V.C puts cyber test detail in the submission ("Security testing documentation and any associated reports or assessments should be submitted"; tester identity and independence level "in the test reports"). So the same parameter (`executor_identity`) is DHF-scope in L1-09 and submission-scope in L1-23. The scope must be per parameter, not per name.

Terminology caution: 21 CFR 820.30(j) (DHF) and 820.30(c) (design input approval, cited in FDA-SW fn 52) were replaced on 2026-02-02 by the QMSR, which incorporates ISO 13485:2016; the current hook is 7.3.10 "design and development file" (FDA-CY itself cites 7.3.10). Keep `dhf` as the scope label but define it as "design and development file / QMS record".

Scope assignments (required parameters in the activated bins; full list in the JSON):

- **dhf**: L2-03.02 `build_environment_toolchain_versions`, `build_date`, `archive_location_ref`; L2-03.04 `last_change_request_implemented_id`, `verification_complete_attestation_date`; L2-05.01 `trace_tool_and_export_date`; L2-05.02 `requirement_version_or_change_date`; L2-05.04 `srs_approver`, `requirements_changed_after_test_execution`; L2-09.01 all four (the test plan is summarised, not submitted); L2-09.02 `protocol_approver`; L2-09.03 and L2-09.05 `test_tools_and_versions`, `executor_identity`, `executor_independence`, `retest_of_run_id`; L2-09.04 `simulators_stubs`, `test_data_set_ids_versions`, `environment_readiness_date`; L2-10.05 `analysis_date`; L2-11.03 `source_system_and_query`, `closed_since_previous_list_count`; L2-04.04 and L2-15.02 per-row `evaluation_date` (use the document approval date as the submission-level surrogate); L2-16.01 `generation_tool_and_version`; L2-28.04 `underlying_evidence_ids`, `evidence_completion_date` (except where FDA-STD Table 1 requires the summary report for a process standard).
